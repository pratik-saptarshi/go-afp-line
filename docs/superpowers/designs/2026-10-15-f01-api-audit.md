# F01 API Audit and Design Decisions

Date: 2026-10-15. Branch: `chore/deferred-f01-api-polish` from `origin/main` @ `5c67179`.
Plan: `docs/superpowers/plans/2026-10-15-deferred-f01-api-polish.md` (R2P2-F01).

Method: `go doc -all` enumeration (51 top-level exported declarations) + caller
grep over non-test code. All test files are internal packages (`package afp`,
etc. — no `*_test` external packages exist), so unexporting breaks no tests.

## a. Exported mutable maps

**`afp.CodePages`** (`afp/codepage.go:29`, `map[uint16]CodePage`).
Direct uses of the map itself: exactly one — `afp/codepage.go:38`, inside
`LookupCodePage`. No test or external use of the map.
**Decision: unexport to `codePages`.** `LookupCodePage` remains the public
access path.

**`line.PinnedFonts`** (`line/line.go:136`, `map[string]FontMetrics`).
Direct uses of the map itself: exactly one — `line/line.go:160`, inside
`LookupFont`. No test or external use of the map.
**Decision: unexport to `pinnedFonts`.** `LookupFont` remains the public
access path.

**Aliasing hazard (found during audit):** `LookupFont` returns `FontMetrics`
by value, but the struct's exported `Advances map[rune]float64` field is
shared by reference — a caller mutating the returned map corrupts the global
table even after the unexport.
**Decision: `LookupFont` returns a defensive copy with a cloned `Advances`
map.** Small, behavior-preserving for readers, closes the mutation hole.

## b. Dead `MaxFieldSize` check — stronger than the panel claimed

`MaxFieldSize = 1 << 20` (1 MiB). `maxSFLength = 32767` (architectural max).

- `DecodeIntroducer` (`afp/sfi.go:113`): `length` comes from
  `binary.BigEndian.Uint16` → max 65535 < 1 MiB. **The check can never fire
  for any input**, not merely "in current call paths". The live guard is the
  `length > maxSFLength` check at line 121.
- `fieldsOp` (`afp/sfi.go:304`): `flen` likewise comes from a uint16 →
  **provably dead**. Worse, it is the documented allocation guard for the
  `make([]byte, flen)` at line 316, and it guards nothing: a field claiming
  65535 bytes allocates 64 KiB and is only rejected later by
  `checkIntroducer`.

**Decisions:**
1. Remove the dead `length > MaxFieldSize` check from `DecodeIntroducer`
   (and its error branch). The `maxSFLength` check stays as the live guard.
2. In `fieldsOp`, replace the dead `flen > MaxFieldSize` check with
   `flen > maxSFLength` — fail fast with `KindStructure` at the field's
   start offset *before* allocation, enforcing the architectural maximum at
   the allocation site as the comment always claimed. Contract delta for
   lengths in (32767, 65535] (reviewer-verified): the offset is unchanged
   (`checkIntroducer` already re-bases to `fieldStart`); what changes is
   (a) fail-fast before the up-to-64 KiB allocation and read, (b) the
   `Reason` text, and (c) `FieldID` goes from populated (e.g. `"D3A8A8"`)
   to empty (the iterator's `fail()` sets none). A test pins the new
   Kind/Offset/Reason/FieldID contract (TDD). Note: `fields_test.go`'s
   `archMax` case (flen=40000) currently asserts introducer-validation
   failure — it must be updated to the new fail-fast contract.
3. Remove the now-unreferenced exported `MaxFieldSize` constant and update
   the stale doc comments at `sfi.go:92` and `sfi.go:314`. Consequential
   updates: delete `TestMaxFieldSize` (`afp/sfi_test.go:155-157`, asserts
   the constant's value — replace with a test pinning the new
   `maxSFLength` iterator bound), fix the `MaxFieldSize` mention in the
   `archMax` comment (`afp/fields_test.go:106`), and update the C13
   iterator contract (`docs/superpowers/designs/2026-10-15-c13-iterator-contract.md`:
   error case 5, the considered-and-rejected rationale for
   `32767 < flen <= MaxFieldSize`, and the allocation section's
   "up to `MaxFieldSize`" language — the change makes the implementation
   match that doc's stated precedence of length-bound checks before
   truncation). Rationale for removal over retention: an exported constant
   whose documented purpose is impossible misleads readers; nothing else
   references it.

## c. Split font tables — claim refuted

Exhaustive case-insensitive search for font/metrics/glyph-advance tables
finds exactly one: `line.PinnedFonts`. No second table exists in `linetopdf`,
`afptoline`, fixtures, or docs. The panel's "split font tables" premise does
not hold against the current tree.
**Decision: no action.** (If the panel meant the `FontMetrics` struct vs.
the `PinnedFonts` map, that is one type plus its sole instance — not a split.)
